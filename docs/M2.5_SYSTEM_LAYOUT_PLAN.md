## A. 目标与非目标

### A.1 目标（M2.5 交付物）

M2.5 把谱面从「按声部各自堆叠」改成「按系统（system）交错」，并给出分页所需的
**纯数据模型**。范围来自 Brief §2.7.6 的 8 条：

| # | 目标 | 本方案落点 |
|---|---|---|
| 1 | 跨声部按小节对齐的统一 spacing（同一 measure 在所有层同宽同 x） | §Q2 / §Q3 / §Q4 |
| 2 | `bracket=N` 把声部连成系统 | §Q1 |
| 3 | 和弦名 → `%%gchord` 按名关联（D11 开启），和弦图就地画在谱上 | §Q5 |
| 4 | TAB beam grouping（清 HANDOFF §30.1 的视觉 debt） | §Q8 / §D **T3.5**（声部内 engraving，组级 demand 喂给 T4） |
| 5 | 简谱减时线纳入系统级对齐（已实现，不新增） | §Q3 消费侧说明 |
| 6 | 歌词跟随简谱行、音节居中 | §D T8（attached layer，不改 system 契约） |
| 7 | page layout model 与 system → page 分配（纯数据） | §Q6 |
| 8 | 行内两端对齐（justify） | §Q4 |

**定位**：M2.5 是**布局架构改造**，不是 engraving 精修。它交付的是
「System Model + Page Model 两个纯数据层 + renderer 从每声部一块改为每系统一块」。

**Staff 的验收口径（裁决）**：**M2.5 的验收标准 = Staff tier 1**（measure 边界与
宽度共享，stave 内音符 x 由 VexFlow `Formatter` 自排，见 §Q3.5）。**T5.S 是非阻塞
spike**：它证明不了 tier 2 不影响 M2.5 验收，证明得了则在其后追加 Staff tier-2
adapter 测试（§Q7.2）。

## B. 架构

### B.1 新目录

```text
src/notation/system/
  contracts.ts     // 纯类型叶子层：SystemLayout / SystemMeasureGeometry /
                   // VoiceLayerLayout / MeasureTimeline / ChordDiagramOverlay /
                   // PageModel …… 零 import（除 domain type-only 与 layout/primitives）
  groupVoices.ts   // Score.voices → SystemGroup[]（bracket/brace/staves 证据）
  measureIdentity.ts // 跨 voice measure 对齐候选 + 结构兼容性校验 + 诊断草案
  timeline.ts      // 小节内 shared timing positions（Rational offsets）与退化判定
  composeSystem.ts // 编排：调三个 voice layout + chord overlay，产出 SystemLayout[]
  justify.ts       // 行内两端对齐 / 剩余宽度分配（纯函数）
  chordOverlay.ts  // chord symbol → 和弦图 overlay（按名精确查表 + 放置几何）
  pageModel.ts     // SystemLayout[] → PageModel（system → page 分配）
src/notation/layout/metrics/system.ts  // system/page 专属尺寸常量（唯一来源）
```

**为什么不塞进 `layout/`**：`layout/` 现在的语义是「跨记谱共享的几何 primitive +
声部内排布算法」（`primitives.ts:2-8`、`spacing.ts:4-6`）。System Composer 需要
**认识三种 voice layout 的产物**，这与 `layout/` 的「谁都不认识」定位冲突。单开
`system/` 目录能让 architecture 守卫把「谁可以 import 谁」写成一条可判定的规则。

### B.2 依赖方向（本轮纠偏③，守卫钉死）

```text
domain ──► notation/system/contracts.ts (纯类型叶子)
                 ▲              ▲              ▲
                 │              │              │
        jianpu/layoutJianpu  tab/layoutTab  staff/layoutStaff   （只 import 叶子层）
                 ▲              ▲              ▲
                 └──────────────┴──────────────┘
                                │
                     system/composeSystem.ts ──► chord/layoutChord
                                │
                     system/pageModel.ts（只吃 SystemLayout[]，不认识 voice layout）
```

三条硬规则：

1. **`system/contracts.ts` 是叶子**：只 type-only import `src/domain` 与
   `notation/layout/primitives.ts`（`Point`/`Box`/`System`），**不 import 任何
   voice layout、不 import composeSystem**。这样三个 voice layout 引用它不会成环。
2. **三个 voice layout 只 import 叶子层**：它们接受 external geometry 的入参类型
   来自 `contracts.ts`，**不得 import `composeSystem` / `chordOverlay` / `justify`**。
3. **`composeSystem.ts` 可以 import 三个 voice layout 与 `chord/layoutChord`**；
   但这不放宽「三个记谱目录互不 import」——那条守卫（`architecture.test.ts:124-161`）
   的 SIBLINGS 判定按文件所在目录做，`system/` 不在 SIBLINGS 里，因此天然不冲突，
   但需**显式补一条**「`jianpu|tab|staff|chord/**` 不 import `system/`
   除 `system/contracts`」的用例（§Q7.4）。

### B.3 数据契约（形状草案，字段名待 T0 拍板）

```ts
// system/contracts.ts —— 全部 readonly，零方法，零 class

/** 一个 system group：哪些声部在同一个方括号 / 花括号 / 竖线里。 */
interface SystemGroup {
  readonly index: number;                    // 文档顺序，0-based
  readonly voiceIds: readonly VoiceId[];     // 层顺序 = Score.voices 的文档顺序
  readonly connector: 'bracket' | 'brace' | 'staves' | 'none';
  readonly evidence: 'declared' | 'singleton'; // declared = 声部上真的写了属性
}

/** 跨声部对齐后的一个 measure 的公共几何。 */
interface SystemMeasureGeometry {
  readonly measureOrdinal: number;  // group 内的对齐序号（不是 Domain 身份，见 §Q2）
  readonly systemIndex: number;
  readonly x: number;               // system box 内的左边界
  readonly width: number;           // 公共宽度（justify 之后的最终值）
  readonly demandWidth: number;     // justify 之前的最大需求宽（诊断/测试用）
  readonly timeline?: MeasureTimeline;  // 缺席 = 本 measure 退出 shared intra timing
  readonly participation: readonly MeasureParticipation[]; // 每个 voice 的参与情况
}

interface MeasureParticipation {
  readonly voiceId: VoiceId;
  readonly kind: 'present' | 'absent' | 'incompatible';
  readonly localMeasureIndex?: number;  // 该 voice 自己的 measure 序号
}

/**
 * 小节内的**共享音乐 onset** 位置（§Q3）。offsets 单调递增，首项恒为 0。
 *
 * **只表示音乐时间**：timed event 的 onset，外加 `chordSymbol` 这种**明确的
 * zero-time overlay**（它贴在后续 onset 上，不新增位置）。
 * **不包含** barline / decoration / grace / unknown —— 它们没有音乐 onset，
 * 强行映射到共享 x 会让同一时间点上的多个事件重叠（见 §Q3.1）。
 */
interface MeasureTimeline {
  readonly offsets: readonly Rational[];        // 小节内累计 onset（仅 timed event）
  readonly total: Rational;                     // 小节内容总时长（= 末 onset + 该事件时值）
  readonly xByOffsetIndex: readonly number[];   // 与 offsets 同序的 measure 内相对 x
  /** measure 右边界的相对 x（= 该 measure 的内容宽）；barline 固定画在这里。 */
  readonly endX: number;
}

/** 一个声部层在某个 system 上的产物引用（不复制几何，只做归属）。 */
interface VoiceLayerLayout {
  readonly voiceId: VoiceId;
  readonly notation: 'jianpu' | 'tab' | 'staff' | 'fallback';
  readonly layerIndex: number;    // system 内自上而下的层序
  readonly top: number;           // 该层在 system box 内的纵向偏移
  readonly height: number;
}

interface ChordDiagramOverlay {
  readonly anchor: Anchor;          // 恒为 event 分支（该 ChordSymbolEvent），见 §Q5.4
  readonly displayText: string;     // chordSymbolDisplayText(raw) 的结果
  readonly shapeIndex?: number;     // Score.chordShapes 的下标；缺席 = 只画名
  readonly x: number;               // system box 内的绝对 x（对齐到所属 offset）
  readonly y: number;               // overlay 带内的基线
  readonly systemIndex: number;
}

interface SystemLayout {
  readonly index: number;
  readonly box: Box;
  readonly groupIndex: number;
  readonly measures: readonly SystemMeasureGeometry[];
  readonly layers: readonly VoiceLayerLayout[];
  readonly chordOverlays: readonly ChordDiagramOverlay[];
  /** 'full' = 拉满行宽；'partial' = 有 measure 触顶 `maxJustifyRatio`，右侧留白；'none' = 未拉伸（如末行）。 */
  readonly justified: 'full' | 'partial' | 'none';
}

/**
 * compose 的产物包装（§Q6.4）。**`SystemLayout` 自身不带 `target` 字段**——
 * 版式目标是这一次 compose 的属性，不是每个 system 的属性。`pageModel()` 的入参
 * 类型只接受 `target: 'page'`，屏幕产物在编译期就传不进去。
 */
interface ComposedSystemLayout {
  readonly target: 'screen' | 'page';
  readonly systems: readonly SystemLayout[];
}

interface PageModel {
  readonly pages: readonly {
    readonly index: number;             // 0-based
    readonly contentBox: Box;           // 页面内容框（页边距内）
    readonly headerBox: Box;            // 页眉占位（首页/续页高度可不同）
    readonly footerBox: Box;            // 页脚占位（页码）
    readonly systemIndices: readonly number[];
    readonly overflow: boolean;         // 该页唯一的 system 仍高于内容框（§Q6.6）
  }[];
  readonly pageSpec: PageSpec;          // 纸张/边距/页眉页脚高度（来自 metrics/system.ts）
  readonly barsPerStaffHint?: number;   // 接口预留，M2.5 恒 undefined（Brief §10.18）
}
```

### B.4 与现有 `JianpuLayout` / `TabLayout` / `StaffLayout` 的关系

**改造方式：加一个可选入参，不改返回类型。**

现在三个入口的签名形如
`layoutJianpu(voice, ctx)`（`jianpu/layoutJianpu.ts:98`）、
`layoutTab(voice, ctx)`（`tab/layoutTab.ts:103`）、
`layoutStaff(voice, ctx)`（`staff/layoutStaff.ts:169`），
三者都在内部自己调 `splitMeasures` + `spaceItems` + `layoutSystems` +
`restackSystems`（`layout/systems.ts`）。

M2.5 的改法：

1. 在各自的 `Context` 上新增**可选**字段
   `externalGeometry?: readonly SystemMeasureGeometry[]` 与
   `externalSystems?: readonly System[]`；
2. 字段缺席 → **完全走现在的代码路径**（这保住了 `jianpu.layout.test.ts` /
   `tab.layout.test.ts` / `staff.layout.test.ts` / render matrix 的全部现有断言，
   也让三个 layout 仍可独立调用）；
3. 字段存在 → 跳过自己的 `layoutSystems` / `restackSystems`，measure→system 归属
   与 measure 的 `x`/`width` 全部取外部值；slot 内相对 x 按 §Q3 的规则消费
   `timeline`（有）或自排（无）。

**为什么不是「把换行逻辑搬走」**：那会让三个 layout 失去独立可测性，render matrix
的 `layoutVoiceAs(notation, …)`（`renderMatrix.helpers.ts`）必须整体重写，风险与
收益不成比例。可选入参是**渐进切换**的关键（§D 的 feature flag）。

**两趟布局的归属变化**：现在 jianpu 按歌词行数、tab 按最深时值装饰各自
`restackSystems`（`layoutJianpu.ts:9-14`、`layoutTab.ts:17-25`）。接入 system 之后
这两个「额外高度」不再由各自回填，而是**上报给 composer**，由 composer 决定
system 的总高与各层的 `top`（`VoiceLayerLayout.top/height`）。实现上：voice layout
新增一个纯函数导出 `extraHeightBySystem(...)`（或让 layout 在 external 模式下把
额外高度写进返回值的新字段），composer 汇总后二次调用——**两趟布局的形状不变，
只是第二趟的主语从 voice 变成 system**（Brief §2.7.3 要求沿用 `base + extraHeight`
模型，不要求像素等高）。

### B.5 Renderer：从「每声部一块」到「每系统一块」

现状：`ScoreView.tsx:244-248` 把 `voiceRenders` 逐个渲染成
`<section class="score-voice">`，jianpu/tab 走 `SvgTree`，staff 走
`StaffVoiceView` → `renderStaff`（`ScoreView.tsx:81-111`）。

目标结构：

```text
.score-systems
  └─ section.score-system[data-system-index]        // 每个 system 一块
       ├─ div.system-overlay      (和弦图层，SvgNode)
       ├─ div.system-layer[data-voice-id]  × N      // TAB / Jianpu：SvgNode
       │    └─ svg（viewBox = 该层在该 system 内的局部坐标）
       └─ div.system-layer.staff-host[data-voice-id]  // Staff：VexFlow 独占 host
```

关键点：

- **zoom 语义不变**：仍是「外层 CSS 宽度 = layout 宽 × `cssPixelsPerUnitAtZoom1`
  × zoom」，`availableWidth` 仍由 `computeAvailableWidthUnits` 换算
  （`voiceRender.ts:138-144`、`metrics/shared.ts` 的 `SCORE_VIEW_METRICS`）。
  唯一变化是**宽度写在 system 块上**而不是 voice 块上。
- **Staff 的 VexFlow host 按 system 切分**：现在一个 voice 一个 host
  （`StaffVoiceView.tsx:76`），改成**一个 (system, voice) 一个 host**。`renderStaff`
  接受「这一段 staves」而不是整份 `StaffLayout`——它本来就是按
  `StaffStaveSpec` 循环建 `Stave(x, y, width)`（`renderStaff.ts:15-17`），
  按 system 切片是自然的。host 内部的 y 需要从「全局 y」改成「system 内局部 y」，
  这是 adapter 的一次小改（`fitSvgToContainer` 的 viewBox 随之变小）。
  **DOM 所有权规则不变**：host 内部 React 永不塞 children（`StaffVoiceView.tsx:4-13`）。
- **锚点归属不变**：`data-anchor-key` 仍由 `anchorKey()` 产生
  （`model/types.ts:54`），system 块额外带 `data-system-index`（M3B 会用），
  **不新增 anchor 种类**（本轮纠偏④）。
- **高亮重扫信号不变**：`renderGeneration` 机制照旧（`ScoreView.tsx:132-137`），
  只是回调次数从「每 voice 一次」变成「每 (system, staff voice) 一次」。

## Q1. System Group 如何形成

### Q1.1 证据边界

`bracket=N` 的 spec 原文是「从当前声部起 N 行谱用方括号连接；**不改变声部名显示
方式**」（spec §12.2 表，等级 `CONFIRMED`（help；corpus），语料 7 次 / 7 文件）。
它证明的是**视觉分组**，**不证明节奏同步**（Brief §2.7.2 明确写死这条边界）。
因此 group formation 与 measure alignment 是**两个独立步骤**：Q1 只决定「谁和谁画
在一行里」，Q2/Q3 决定「怎么对齐」。

语料实测（只读脚本，`loadJcx` 后统计）：

| 文件 | 声部数 | bracket |
|---|---:|---|
| corpus#02 / #03 / #04 / #07 / #10 / #11 | 2 | v1 `bracket=2` |
| corpus#09 | 3 | v1 `bracket=3` |
| corpus#01 / #05 / #06 | 1 | 无 |
| corpus#08 | 9 | 无（全部声部无 `style`、无 bracket） |

即：**语料里 `bracket=N` 恒等于「把从当前声部起的全部 N 个声部连成一组」，且恒从
v1 起、N 恒等于文件的声部总数**（7/7 文件）。这与 spec 的定义一致，但**不足以证明
「多个 group 并存」的形态**（语料零样本）——多 group 的行为属 **未核实**，方案按
spec 的字面语义实现，并对越界情形发诊断。

### Q1.2 算法（确定性，纯函数）

输入：`Score.voices`（文档顺序，`src/domain/score.ts:140`）。
输出：`readonly SystemGroup[]`，覆盖全部声部，**无重叠、无遗漏**。

```text
i = 0
groups = []
while i < voices.length:
    v = voices[i]
    n = connectorSpanOf(v)          // 见下
    if n === undefined or n <= 1:
        groups.push(singleton(v));  i += 1
    else:
        span = min(n, voices.length - i)          // 越界截断 + 诊断
        groups.push(group(voices[i .. i+span-1], connectorKindOf(v)))
        i += span
```

`connectorSpanOf(v)` 的优先级（本期只实现 `bracket`，其余留接口）：

1. `v.bracket !== undefined` → `('bracket', v.bracket)`；
2. `v.brace !== undefined` → **本期不实现**：当作 `singleton`，并发一条
   info 诊断「`brace` 已解析但本版不渲染花括号连接」（spec §12.2 里 `brace` 是
   `DOC-ONLY`、**仅 faq**、语料 0 次）；
3. `v.staves !== undefined` → 同 2（`DOC-ONLY`，语料 0 次）；
4. 都没有 → `singleton`。

**未被任何 group 包住的 voice** → 自成一个单 voice system group
（`connector: 'none'`, `evidence: 'singleton'`）。这保证：

- corpus#01 / #05 / #06（单声部）行为与今天**完全一致**——一个 group 一个 voice，
  system 就是今天的 system；
- corpus#08（9 声部、无 bracket）**不会**被强行连成一个 9 层的巨型 system；它们
  是 9 个单 voice group，纵向仍然是堆叠的 9 组 system。这正是保守解：没有分组证据
  就不分组。

### Q1.3 group 之间的纵向顺序

group 按**文档顺序**依次排下去；同一 group 内的层顺序 = `Score.voices` 的文档顺序
（`VoiceLayerLayout.layerIndex`）。

**不按 profile 重排层序**：Brief §2.7.0 的「Guitar Arrangement System Profile」
描述的是「和弦图 → 六线谱 → 简谱 → 歌词」的四层，而语料里 TAB 声部恰好就写在
jianpu 声部之前（corpus#02/#03/#04/#07/#09/#10/#11 全部是 v1=tab、v_last=jianpu），
**文档顺序自然产生目标层序**。因此不需要「按 notation 类型排序」的规则——那会在
作者故意把 jianpu 写在前面时擅自改变他的意图。

> **依据**：Brief §2.7.0 明写这是 *一个* profile 而不是唯一版式；层序来自文档顺序
> 是最小承诺。若将来要支持 profile 级重排，挂在 `SystemGroup` 上加一个
> `layerOrder?: readonly VoiceId[]` 即可，不动本算法。

### Q1.4 接口预留（`brace` / `staves`）

- `SystemGroup.connector` 是**四值联合**（`bracket` / `brace` / `staves` / `none`），
  本期只会产出 `bracket` 与 `none`，另两个值由类型系统占位；
- 渲染端读 `connector` 决定画什么连接符号（本期：`bracket` 画方括号，`none` 不画）；
  遇到未来产出的 `brace`/`staves`，渲染端必须走 `switch` 穷尽分支，**新增值会在编译期
  点亮所有消费点**（与 `spacing.ts:79-102` 的 `timedDurationOf` 同一手法）；
- `brace` 还带「声部名标在花括号中间」的语义（spec §12.2），`staves` 带「声部名标在
  竖线中间」——这两条**不在 M2.5 实现**，但 `SystemGroup` 里已经有 `voiceIds`，
  将来取名字不需要改契约。

## Q2. 跨声部 measure identity 如何建立

### Q2.1 为什么不能按「第 N 个 measure」默认语义一致

语料实测（`splitMeasures` 的同口径：以 `BarlineEvent` 为切点，
`layout/systems.ts:68-89`）：

| 文件 | 各声部 measure 数 | 结论 |
|---|---|---|
| corpus#03 / #04 / #07 / #09 | 完全一致（53/53、23/23、22/22、39/39/39） | 序号可直接对齐 |
| corpus#02 | 68 vs 69 | **不一致** |
| corpus#10 | 59 vs 61 | **不一致** |
| corpus#11 | 22 vs 23 | **不一致** |
| corpus#08 | 40/40/40/38/40/40/40/25/14 | **严重不一致**（但无 bracket，属 9 个单声部 group） |

即：**有 bracket 的 7 个文件里，3 个的声部 measure 数不一致**（corpus#02/#10/#11）。
按序号硬对齐会在这 3 个文件上把整行错位——这不是理论风险，是语料现实。

**关于 measure 时值总和（U06 已结案并修复完成）**：本方案初稿在修复前测得
corpus#02/#10/#11 的两个声部每个 measure 的时值总和恒差 2 倍（3/4 拍 0.750 vs
1.500；4/4 拍 1.000 vs 2.000）。成因是 **U06 的 parse bug**——body 区 inline `L:`
泄漏到了其它声部的 `unitLengthChanges`。

**修复已合入 `8a74e8e`**（`L:` 按所在声部作用域生效），三平台 CI 全绿，
全量 **74 文件 / 5712 用例**、fixture **104/104**、corpus **11/11**。

**已重测**：系统性 2× 偏差消除；corpus#02 / #03 / #04 的简谱声部对 TAB 声部为
**1.000×**，corpus#10 为 **0.984**、corpus#11 为 **0.957**——两处残差来自**零时值
小节**（该声部在对应 ordinal 上存在只含小节线 / 无计时内容的 measure），不是比例
缩放。因此：

> **结论（与 §Q2.3 的校验模型一致）**：U06 的**系统性 2× 偏差已经消除**；绝对
> `Rational` 现在**可以直接比较**，但**相等仍必须逐候选 measure 验证，不预设相等**；
> **不等即进入 tier 3**（该 measure 只共享边界与宽度，不共享内部时间位置）。
> 初稿里为绕开 U06 而设计的时值比例校验与归一化 offset **已全部删除**，
> 不留开关、不留回退分支。
>
> measure **数**的 mismatch 与 `L:` 无关（`splitMeasures` 只按 `BarlineEvent` 切分），
> 上表的 68/69、59/61、22/23 在修复后**保持不变**，已复核。

### Q2.2 Domain 没有 measure identity（纠偏②）

Domain 的 `Voice.events` 是扁平事件流，**没有 measure 概念**
（`model/types.ts:4-6`、`layout/systems.ts:3-5` 都写死了这条）。M2.5
**不新增 `MeasureId`、不改 Domain**。跨声部 measure identity 写成：

```text
measure identity := ordinal candidate  +  structural compatibility validation
```

- **ordinal candidate**：以 group 内各声部各自的 measure 序号（`MeasureSlice.index`，
  `layout/systems.ts:26-33`）作为对齐**候选**；`measureOrdinal` 只是这个候选的编号，
  **不是 Domain 身份**，不回写任何地方，不参与序列化。
- **structural compatibility validation**：候选要经过下面的结构特征校验才被采纳。

### Q2.3 结构兼容性校验（逐条可判定）

对 group 内的每个 `measureOrdinal = k`，取各声部第 k 个 `MeasureSlice`，计算四个
结构特征：

| 特征 | 取法 | 依据 |
|---|---|---|
| S1 尾小节线形态 | 该 slice 最后一项若是 `barline`，取其 `raw`（`|`/`|]`/`:|`/`|:` …） | spec §18 表；`layout/systems.ts:8-11`「小节线收尾它所结束的 measure」 |
| S2 是否只含一根线 | `items.length === 1 && items[0].kind === 'barline'`（开头孤立 barline 的形态） | `layout/systems.ts:64-66` 明写这种 measure 会产生 |
| S3 内容时值总量 | 该 slice 内 `timed` 事件的 `duration` 之和；有 `undefined` 则标 unresolved | `spacing.ts:79-102` 的 `timedDurationOf` 同口径 |
| S4 是否尾巴（无终止线） | 该 slice 最后一项不是 barline | `layout/systems.ts:66` |

判定规则（按顺序，先命中先决定）：

1. **C1 计数一致**：group 内所有声部 measure 数相等 → 全部 ordinal 候选采纳，
   逐个进入 C2/C3 校验。
2. **C2 结构对齐**：对每个 k，若各声部的 S1 形态**互不冲突**（定义：所有存在的 S1
   要么相等，要么其中一方缺席），且 S2/S4 不出现「一方是孤立线、另一方是内容小节」
   这种形态冲突 → **采纳**，`participation.kind = 'present'`。
3. **C3 时值总量一致**：S3 各声部的时值总量按 **绝对 `Rational` 相等**比较
   （精确有理数比较，零浮点）。相等 → **兼容**；不等 → 该 measure 标
   `incompatible`（进而退出 shared intra-measure timing，见 §Q3.3 的 D3）。
   某声部该 measure 含 `duration === undefined` 时该项**不参与比较**，直接按
   §Q3.3 的 D1 退出 tier 2。
4. **计数不一致**：group 内 measure 数不等（corpus#02/#10/#11）→ **不做任何序列
   对齐搜索**（LCS / DTW 一律不用：那是在猜作者意图，且不确定性高）。采取
   **前缀对齐 + 尾部留空**：`measureOrdinal` 取 `max(count_v)`，超出某声部范围的
   ordinal 对该声部记 `participation.kind = 'absent'`；该层在该 measure 留空，
   **但公共宽度仍由参与的声部决定**（Brief §2.7.2 的第②条原文「该层留空，但保留
   公共宽度」）。同时发一条 group 级诊断（见 Q2.5）。
5. **明显冲突**：某 k 上出现 S1 形态互斥（如一方 `|:` 一方 `|]`）或 S2/S4 形态冲突
   → 该 measure 标 `incompatible`，**退出 shared intra-measure timing**
   （`timeline` 缺席，见 §Q3），但**仍共享 measure 边界与公共宽度**（tier 1 不放弃），
   并发诊断。
6. **弱起 / 不完整小节**：首 measure 的 S3 小于该声部的众数 measure 时值 → **不做
   任何特殊处理，也不报错**。理由：JCX 无 anacrusis 标记（spec 未定义），`Meter`
   不参与任何列宽计算（`spacing.ts:9-10` P1-3），「不完整」这个判断需要拍号语义，
   属臆造。弱起小节就是一个内容较少的 measure，按内容需求定宽即可。弱起小节在
   C3 里与其它 measure 同等对待：只要 group 内各声部该 measure 的绝对时值总量相等，
   它就是兼容的（弱起是**各声部同时**变短，不会单独造成不等）。
7. **开头孤立 barline**（`|: CDE` 产生的只含一根线的 measure，
   `layout/systems.ts:64-66`）：若 group 内**只有部分声部**有这个孤立小节，会让后续
   全部 ordinal 错位一格。规则：**孤立起始 measure 参与 ordinal 编号，不做合并**
   （与 `splitMeasures` 保持同一口径，绝不「替作者判断这根线属于哪一小节」），
   若因此导致 C2 在 k=0 上冲突，则按规则 5 标 `incompatible` 并发诊断——**不静默
   移位对齐**。

> **为什么不做序列比对**：Brief §2.7.2 的保守版本只承诺三档（对齐 / 留空保宽 /
> fallback+诊断）；序列比对会引入「同一份文件在不同版本产生不同对齐」的风险，
> 与确定性要求（`spacing.ts:20`、`systems.ts:17`）冲突。若将来需要，它是
> `measureIdentity.ts` 内部的一个可替换策略，契约不变。

### Q2.4 降级顺序（三档，逐级下降，绝不重写事件）

```text
tier 1  共享 measure 边界 + 公共宽度（本期恒成立，除非 group 只有一个 voice）
tier 2  共享 intra-measure timing positions（需要 §Q3 的全部前提成立）
tier 3  各层在公共 measure 框内自行排布（tier 2 失败时的落点）
```

**任何情况下都不下降到「各声部各自换行」**——那等于退回 M2 现状。tier 1 是 M2.5
的硬承诺。

### Q2.5 新增诊断码（只追加）

| code | level | 触发 | anchor |
|---|---|---|---|
| `muse.render.system.measure-count-mismatch` | warning | group 内各声部 measure 数不等，已按前缀对齐并对缺失层留空保宽 | **group 内每个声部各一条 voice anchor**（见下） |
| `muse.render.system.measure-structure-conflict` | warning | 某 measure 的小节线形态 / 结构特征冲突，已保留公共边界但放弃该小节的内部时间对齐 | 该 measure 在**该声部**的首个事件的 **event anchor**；该 measure 在该声部为空时退回 voice anchor |
| `muse.render.system.measure-timing-degraded` | info | 该 measure 退出 shared intra-measure timing（时值不可知 / tuplet 未建模），各层在公共框内自排 | 同上 |

**anchor 选择理由**（纠偏④，只用现有四种 Anchor 分支，**不新增 system/measure
anchor**）：

- `measure-count-mismatch` 是**声部之间**的事实，没有单一事件可挂；挂 voice anchor
  让 UI 能把提示定位到左栏的声部卡片（Brief §3.4 的联动诉求），且 C3 的 voice 分支
  必然可解析。**每个相关声部各发一条**而不是发一条挂在某一个声部上——后者会让
  「另一个声部为什么错位」在 UI 上无处可点。
- `measure-structure-conflict` / `measure-timing-degraded` 有明确的发生位置
  → 用该 measure 首个事件的 event anchor，点击可直接跳到谱面那一小节
  （M3B 的三向联动会复用）。C3 的 event 分支要求 `voiceId` 一致
  （`renderMatrix.helpers.ts` 的 ownership 断言），用该声部自己的事件天然满足。

## Q3. 小节内部怎么真正对齐（最关键）

### Q3.1 为什么不能按 slot index 对齐

`TimeSlot.index` 是「该声部内的列序号」（`layout/primitives.ts:47-54`，注释明写
「跨声部对齐不在 M2 范围……所以这里不带 voice 维度」）。同一小节里 TAB 层可能有 8 个
`tabGroup` + 1 根 barline + 4 个零宽 chordSymbol overlay，简谱层可能只有 4 个 note
+ 1 根 barline——列数根本不同。按下标对齐会把简谱第 2 个音对到 TAB 第 2 个音，
而它们在时间上可能差半拍。

### Q3.1b 两层契约：共享音乐时间 vs voice-local 视觉 slot（**关键设计点**）

初稿把 barline / decoration / grace / unknown 也记到「当前 `off`」上，再让
Jianpu/TAB 在 external 模式按 `offset → x` 摆放。这会立刻出两个错：

1. **重叠**：同一个 onset 上若同时有 decoration、grace 与正常音符，它们会拿到
   **同一个 x**，互相压在一起——而这几类事件在 M2 里本就是各占一个
   `untimedSlotWidth` 的窄列（`spacing.ts:136-139`）。
2. **barline 位置错**：小节线的 x 不该由「它自己那一项的 offset」决定，而应固定在
   **measure 右边界**（`layout/systems.ts:8-11`：小节线收尾它所结束的那个 measure）。

因此契约分两层：

| 层 | 内容 | 谁决定 x |
|---|---|---|
| **共享音乐时间层** | timed event 的 **onset**；`chordSymbol` 这种**明确的 zero-time overlay**（贴在后续 onset 上，不新增位置） | `MeasureTimeline.offsets → xByOffsetIndex`（跨声部统一） |
| **voice-local 视觉层** | `barline`、`decoration`、`grace`、`unknown` | 各 voice 自己的 slot / attachment 几何；**barline 固定在 `timeline.endX`**（measure 右边界） |

> **一句话**：`offset → x` **只约束需要跨声部对齐的音乐时间位置**，不是「小节内所有
> 事件的定位表」。voice-local 层照旧用现有的 `SpacedSlot` 相对 x（按段宽等比拉伸），
> 这保住了 M2 已经调好的窄列几何，也让 C1 的「每事件恰好一个节点」不受影响。

### Q3.2 shared timing positions 的构造

对一个通过 tier 2 前提的 measure：

```text
对每个参与声部 v：
    off = 0
    for item in measureSlice(v).items:
        if item 是 timed event（note/rest/chord/tabNote/tabGroup 且 duration 已知）:
            onsetOf(item) = off                  # 进入共享层
            off += duration
        elif item.kind === 'chordSymbol':        # 明确的 zero-time overlay（Q3.4）
            overlayOnsetOf(item) = off           # 贴在后续 onset 上，不新增共享位置
        else:                                    # barline / decoration / grace / unknown
            （不进共享层；barline 记为 measure 右边界，其余走 voice-local slot）
    totals[v] = off
```

**直接用绝对 offset**：`offsetOf(item)` 就是该事件在小节内的累计 `Rational` 时值，
**不做任何归一化、不除以 measure total**（U06 修复后跨声部绝对时值可比，见 §Q2.1）。

`MeasureTimeline.offsets` = 各声部 **timed onset** 的**并集**，按升序去重（`Rational`
的精确相等比较，零浮点——与 `duration.ts:35` 的「全程整数 / BigInt 运算，无浮点」
同一纪律）。首项恒为 `0/1`，`total` = 各声部 `totals[v]`（C3 已断言它们相等）。
`endX` 是 measure 右边界（§Q3.6）。

每个 voice 于是得到一张 **`onset → slotIndex`** 的映射（实现上是
`Map<offsetKey, slotIndex>`，`offsetKey` 取 `` `${num}/${den}` `` 的约分形式）；
**只覆盖 timed event**，其余事件不在这张表里。
这是**布局产物索引**，不是 Domain lookup，architecture 守卫明确允许
（`architecture.test.ts` 的「允许布局用途的位置索引」用例）。

> **为什么可以直接用绝对值**：初稿曾因 U06 的 `L:` 泄漏 bug 而设计过归一化
> （除以各自 measure total）的方案；U06 结案修复后，同一 group 内各声部的绝对
> 时值本就应当相等，C3 已经把「不相等」挡在 tier 2 之外（标 `incompatible` →
> tier 3）。因此**不需要任何缩放**：真的时值不同的两个声部**不应当**被强行拉齐，
> 让它们各自在公共 measure 框内自排才是诚实的呈现。

### Q3.3 退化判定（纠偏①，逐条精确）

**退出 shared intra-measure timing（tier 2 → tier 3）的充分条件**，只有这些：

| 条件 | 判据 | 依据 |
|---|---|---|
| D1 时值未知 | 该 measure 内任一 timed 事件的 `duration === undefined` | `spacing.ts:140-143`（`kind: 'fallback'`）；该 measure 本来就整体退等距（§2.6.1 R4） |
| D2 tuplet effective timing 未建模 | 该 measure 内有事件属于某个 `Tuplet` 关系 | `relations.ts:234-246` 发 `tupletTimingNotModeled`；`duration.ts:9-12` 明写不按 `p/q` 推算 |
| D3 结构冲突 | Q2.3 规则 5 判定的 `incompatible` | 本方案 Q2.3 |
| D4 时值总量不等 | Q2.3 规则 3 的绝对 `Rational` 总量比较不相等 | 本方案 Q2.3 |

**明确不是退化条件**（纠偏①）：

- **`durationUnrepresentable`（`1/3`、`5/16`）不退化**。它的 `Rational` 是**已知**的，
  只是画不出时值装饰。`spacing.ts:16-18` 原文：「不可表示的 `duration`（`1/3` /
  `5/16`）不走等距……它的时值是已知的，只是画不出时值装饰，这与「时值根本不可知」
  是两件事」。因此它**照常按字面 `duration` 参与小节内累计 offset**。
- **`brokenRhythm` 不需要二次处理**。parse 层已经把倍率**改写进 Domain 的
  `duration` 最终值**：`src/formats/jcx/parse/body/pairBrokenRhythm.ts:2-8` 原文
  「通用倍率（n = 符号个数）：`a>b` 前音 ×(2 − 1/2ⁿ)、后音 ×1/2ⁿ……改写产出**新的
  事件对象**（`id` 与 `durationRaw` 均不变：`durationRaw` 是事实，改写后的
  `duration` 是 §1.7 允许进 Domain 的派生值）」，Domain 侧 `BrokenRhythm` 的注释
  同样写明「本关系只存原拼写与两端事件引用，**不重复存倍率**」
  （`src/domain/relation.ts:88-96`）。System Layout **直接消费 `duration`，不再次
  应用任何倍率**。
- **`Z` / `@` 休止**不退化：它们有 `duration`，照常累计（`Z` 的多小节语义未建模已由
  `restMultiMeasureNotModeled` 在 event 级报过，本层不重复报）。

tier 3 的行为：`SystemMeasureGeometry.timeline` 缺席，各 voice layout 在
`[x, x+width]` 这个公共框内**用自己现有的 slot 逻辑排布**（jianpu/tab 用
`spaceItems` 的相对 x 再按 `width/demandWidth` 等比拉伸；staff 交给 Formatter）。
**只保证公共 measure 边界与宽度，不猜节奏位置**。

### Q3.4 chordSymbol 是 zero-time overlay

`spacing.ts:126-131` 已经把和弦符号定死成零宽 overlay 列：「和弦符号（spec §25）
标注「此处开始是这个和弦」，不消费节奏时间」。因此：

- 它**不推进** `off`，其 `offsetOf` 等于**后续第一个有实际列宽事件**的 offset；
- 位于 measure 末尾时 offset 等于该 measure 的 total（即 measure 末端）
  （`spacing.ts:45-50` 的 overlay 不变量，消费方必须保持）；
- 它因此天然获得一个「挂在哪个共享时间位置上」的答案 → §Q5 的和弦图 overlay 直接
  复用这个 offset，**不需要第二套定位规则**。

### Q3.5 三种记谱各自如何消费 shared timing

**Jianpu**（`layoutJianpu.ts:110-125`）：现在 x = `placement.x + slot.slot.x`。
改成（external 模式，**逐类分派**，见 §Q3.1b）：

| 事件类 | x |
|---|---|
| **timed event**（有 onset） | `geometry.x + timeline.xByOffsetIndex[i]`，`i` = 该 onset 在 `offsets` 里的下标 |
| **`chordSymbol`**（明确 overlay） | 取它所贴附的后续 onset 的 x；贴在 measure 末尾时取 `geometry.x + timeline.endX` |
| **`barline`** | `geometry.x + timeline.endX`（measure 右边界；measure 首项的孤立起始线取 `geometry.x`） |
| **`decoration` / `grace` / `unknown`** | **voice-local**：按该 voice 自己的 `SpacedSlot` 相对 x 在所属段内等比摆放，**不查共享表** |

`timeline` 缺席（tier 3）时全部退回 `slot.slot.x × stretch`。**列宽仍由自己算**
（下一个共享位置减当前位置就是本段的可用宽），减时线 / 延音线的最小宽需求照旧通过
`widenForJianpuGlyphs`（`jianpuSlotWidths.ts:98`）上报给 §Q4 的需求求解，**不被压缩**。

**TAB**（`layoutTab.ts:139-163`）：同构，逐类分派规则相同。beam grouping（§D T3.5）
是**声部内 engraving**，用该 voice 自己的小节内 onset 判拍边界，**不依赖共享
timeline 是否成立**（§Q8.1）。

**Staff**：这是唯一不同构的一层。`layoutStaff.ts` 只给每个 (system, measure) 一个
`StaffStaveSpec{x, y, width}`（`staffTypes.ts:260-271`），**stave 内音符 x 由
VexFlow 的 `Formatter.formatToStave` 决定**，`slot.x` 明确「是 packing 的输入，
不是最终音符 x」（`layoutStaff.ts:11-14`、`renderStaff.ts:15-17`）。

因此 Staff 的对齐分两档（纠偏⑥）：

- **tier 1（M2.5 承诺）**：measure 边界与宽度共享。做法：`StaffStaveSpec.x/width`
  直接取 `SystemMeasureGeometry.x/width`（减去行首预留的处理见下），
  `Formatter` 在这个宽度内自排。这一档**只需要改 `layoutStaff` 的入参消费**，
  无 VexFlow 风险。
  - 行首预留的既有几何必须保持：`layoutStaff.ts:16-31` 说明 reserve 是**行首 stave
    自己的一部分**（行首 `width = 内容宽 + reserve`，非行首 `x += reserve`）。接入
    system 后，reserve 要在**公共宽度求解之前**从可用宽度里扣（§Q4.4），否则整行会
    被挤超宽。
- **tier 2（不承诺，需 spike 证明）**：stave 内音符 x 与 jianpu/TAB 精确对齐。
  三条候选路径与评估：
  1. **`Formatter.format(voices, justifyWidth)` + 共享 tick context**：把同一 group
     的 staff voice 与一个「按共享 offsets 构造的隐形参考 voice」一起
     `joinVoices` 后再 format，让 VexFlow 的 tick context 把相同时刻的 tickable
     对齐。**可行性未核实**——需要验证 (a) `joinVoices` 能否接受由本层合成的
     参考 voice，(b) VexFlow 的 tick 分辨率能否表达小节内累计的 `Rational` offset，
     (c) `VoiceMode.SOFT` 下 tick 不匹配是否仍不抛（`renderStaff.ts:20-21` 只保证
     不抛，不保证对齐语义）。
  2. **按共享位置切成多个窄 Stave**：每个共享 offset 一个 stave。会破坏谱线连续性
     与符尾，**不推荐**。
  3. **format 之后读回 tickable 的实际 x，再整体仿射修正**：只能整体平移/缩放，
     无法逐音修正，**只能改善不能保证**。
  - **spike 目标与验证方法**见 §D T5.S 与 §E-1。**未证明前，Staff 只承诺 tier 1**，
    方案与测试都按 tier 1 写，tier 2 的差异以「已知限制」记入文档。

### Q3.6 `MeasureTimeline` 的 x 求解

`xByOffsetIndex[i]` 的求法（measure 内相对 x，起点 0）：

```text
segWidth[i] = 第 i 个共享 onset 到第 i+1 个共享 onset 之间，所有参与声部的最大宽度需求
              —— 需求含该段内的全部 voice-local 事件（decoration / grace / unknown 的窄列
                 与 beam 组的组级需求都落在它们所属的段里）
x[0] = 0;  x[i+1] = x[i] + segWidth[i]
endX  = x[last] + segWidth[last]          # 末段：最后一个 onset 到 measure 末端
```

要点：

- **voice-local 事件不新增共享位置，但要计入所在段的宽度需求**——否则同一 onset 上
  的装饰会把音符挤出段外。这正是「时间位置共享、视觉 slot 不共享」的落点。
- **`endX` 是 barline 的 x**，也是 measure 的内容宽（justify 前的 `demandWidth`）。
- 「最大宽度需求」的定义与来源见 §Q4.2。这保证：**任一声部的任一列都不会被另一个
  声部的窄 spacing 压缩**（§Q4 的硬要求）。

## Q4. 公共 measure width 如何求解

### Q4.1 三步管线

```text
① 每个 voice 对每个 measure 给出 minimum width demand（含 notation-local visual minimum）
② system composer 对同一 measure 取各 voice 需求的 max → demandWidth
③ 用 demandWidth 做 line packing（贪心，沿用 layoutSystems 的规则），再 justify 剩余宽
```

### Q4.2 demand 的来源（不新造，复用现有三条链路）

| voice | demand 来源 | 依据 |
|---|---|---|
| jianpu | `widenForJianpuGlyphs(spaceItems(...))` 的 `MeasureSpacing.width` | `jianpuSlotWidths.ts:98-110`（延音线 dash 的最小展开宽） |
| tab | `widenForTabGlyphs(...)`（含文本量宽） | `tabSlotWidths.ts:140-152` |
| staff | `widenForStaffGlyphs(...)` + 行首 reserve（仅行首 measure） | `staffSlotWidths.ts:61-73`、`layoutStaff.ts:16-31` |

这三个函数都是「时值加权列宽 与 字形最小宽 取 max」（`Math.max(spacedSlot.slot.width,
required)`），语义正是「minimum width demand」。M2.5 **把它们从 layout 内部提升为
可单独调用的导出**（纯函数，不改逻辑），composer 在 compose 之前先调一遍拿需求，
voice layout 之后再用最终几何跑一遍摆字形。**同一函数两次调用、同一输入 → 同一结果**
（三者都已是纯函数，`layoutJianpu.ts:95-96` 等有确定性声明）。

细粒度：需求不仅是 measure 总宽，还包含**逐共享位置的段宽需求**（§Q3.6 的
`segWidth`）。做法：把每个 voice 的每一列按其 offset 归到共享位置，同一段内多列的
宽度求和，再跨 voice 取 max。

### Q4.3 line packing

沿用 `layoutSystems` 的贪心规则（`layout/systems.ts:97-130`）：按 measure 顺序累加
`demandWidth`，超出可用宽就换行；**单个 measure 宽于容器时独占一行不再拆**
（同一条裁决 D7，理由是拆小节需要迭代重排）。差别只有一个：输入从「某个声部的
measure 宽」变成「group 的公共 measure 宽」，因此 group 内所有层**必然同步换行**。

### Q4.4 行首预留的处理

Staff 每行要重画谱号/调号/拍号（`layoutStaff.ts:16-18`，产品决定）。TAB 行首要画
竖排 `TAB` 字样（Brief §2.7.2 第 2 层）。规则：

- group 的**行首预留 = 各层行首预留的最大值**；
- 在 packing **之前**从 `availableWidth` 里扣掉（与 `layoutStaff.ts:189-190` 的
  既有做法同构：排完再补会把行首那一小节挤超宽）；
- 预留出的空间**加在行首 measure 的公共宽度上**，不整行右移（`layoutStaff.ts:20-27`
  已论证过：谱号画在 stave 内部，整行右移会留死区）。

### Q4.5 justify（两端对齐）的分配规则

行剩余宽 `slack = availableWidth − Σ demandWidth(该行)`。

**规则：按各 measure 的 `demandWidth` 成比例分配，不按时值比例、不均分。**

```text
extra(m) = slack × demandWidth(m) / Σ demandWidth
width(m) = demandWidth(m) + extra(m)
```

measure 内部，段宽同样按 `segWidth` 成比例放大（因此共享位置的相对关系被保持，
不会出现「拉伸后简谱与 TAB 错位」）。

**理由**（三选一的取舍）：

- **不按时值比例**：时值比例需要拍/时值语义，而 `Meter` 不参与任何宽度计算
  （`spacing.ts:9-10` P1-3），且 tuplet / 不可表示时值 / `duration===undefined`
  三种情形下时值根本不可用。按时值分配会在这些 measure 上产生与 demand 相反的
  结果（时值长但内容少的 measure 被继续放大）。
- **不均分**：均分会把「一个音的小节」和「十六个音的小节」拉成一样宽，视觉密度
  跳变。
- **按 demand 比例**的实质是「内容多的小节多分一点」，与现有列宽模型
  （时值加权 + 字形最小宽取 max）是同一套密度语义的自然延伸，且**不需要任何新事实**。

**最后一行不 justify**（默认）：参考图的行末参差是正常记谱惯例；仅当该行是唯一
一行、或剩余宽小于阈值时同样不拉伸。→ 这一条是 **§F 的 F-3 裁决**（是否所有行
都拉满），推荐默认「末行不拉伸」。

**上限保护 = water-filling 迭代**：`SYSTEM_METRICS.maxJustifyRatio` 限制单个 measure
最多放大到 `demandWidth × R`（避免只有一个小节的行被拉成整页宽）。它**不是**一次性
截断，而是逐轮收敛：

```text
free = 该行全部 measure;  slack = availableWidth − Σ demandWidth
loop:
    按 demandWidth 比例把 slack 分给 free 中的 measure
    若某些 measure 因此超过 cap(m) = demandWidth(m) × R:
        把它们固定在 cap(m)，从 free 移出，
        slack ←（剩余未分配量 + 被截掉的超出量），回到 loop
    否则收敛，退出
```

终止条件与标记：

- 收敛且 `free` 非空 → 该行 `Σwidth === availableWidth`，`justified = 'full'`；
- **全部 measure 都触顶仍有 slack** → **不再拉伸，剩余宽留在行右侧空白**，
  `justified = 'partial'`；
- 该行按策略不拉伸（如末行，§F-3） → `justified = 'none'`。

迭代必然终止（每轮至少固定一个 measure，`free` 单调减小），且全程有理数/确定性。
阈值 `R` 是**产品决定**，写进 `metrics/system.ts`。

### Q4.6 不让一个 voice 的窄 spacing 压缩另一个 voice

这条在管线里是**结构性保证**而不是检查：② 与 §Q3.6 都只做 `max`，从不做 `min`
或平均。形式化不变量（测试直接断言，§Q7）：

```text
∀ measure m, ∀ voice v:  width(m) ≥ demand_v(m)
∀ 共享段 s, ∀ voice v:   segWidth(s) ≥ demand_v(s)
```

### Q5.1 查表规则（精确字符串匹配，零归一化）

### Q5.2 carrier / source selection（纠偏⑤）

语料事实：**全部 chordSymbol 都只出现在 TAB 声部**（corpus#02/#03/#04/#07/#09/#10/
#11 的 v1，以及单声部 corpus#05 的 staff 声部），jianpu 声部恒为 0 条。

但规则不能依赖这个巧合。确定性规则：

1. **carrier voice** = group 内**文档顺序最靠前、且至少含一个 `ChordSymbolEvent`**
   的声部。它的和弦符号构成 overlay 的基准集合。
2. 其它声部在**同一共享 offset**上的 `ChordSymbolEvent`：
   - **显示文本相同** → 去重，只画一个 overlay（anchor 取 carrier 那条事件）；
   - **显示文本不同** → **两个都画名**（横向并排，碰撞处理见 Q5.3），并发一条
     `muse.render.chord.symbol-conflict`（新码，warning），anchor 挂**非 carrier
     那一条事件的 event anchor**（冲突的「另一种说法」在哪里，用户点的就是哪里）。
3. 某声部的 chordSymbol 落在**该 measure 已退出 shared timing**（tier 3）时：该条
   overlay 仍然画，但 x 取「该 measure 左边界 + 该声部自排结果里该事件的 x」，并计入
   `measure-timing-degraded` 已发的那条诊断，**不再单发**。
4. **绝不静默丢弃任何一条 `ChordSymbolEvent`**：C1 契约要求每个事件恰好一个 primary
   可见节点（`renderMatrix.helpers.ts` 文件头）。注意 **overlay 不是 primary node**
   ——和弦符号在 TAB/Jianpu 层已经有它的 primary 节点了（`spacing.ts` 的 overlay 列
   对应各记谱的和弦符号字形）。**chord diagram overlay 是第二个可见产物，必须住在
   `SystemLayout.chordOverlays` 而不是任何 `layout.nodes` 里**——否则 C1 立刻从 1
   变成 2（这正是 `TabStrokeMark` 当初踩过的坑，见 `renderMatrix.helpers.ts` 文件头
   「实测各 overlay 的 anchor 分布」段）。

### Q5.3 overlay 的放置几何

- **层位**：和弦图层是 system 的**第 0 层**（最上），位于最上面那个 voice 层
  （通常是 TAB）之上（Brief §2.7.2 第 1 层）。
- **x**：对齐到该 chordSymbol 的共享 offset 的 x（§Q3.4 已经给出 offset），
  即「在对应 measure / offset 的正上方」；和弦变化出现在小节中途时同样成立
  （Brief §2.7.2 明写「也会出现在小节中途」）。
- **名与图的关系**：**和弦名在图的上方**（Brief §2.7.2 / §10.16 裁决），
  `ChordLayout` 本身已经把 name 画在网格上方（`chord/layoutChord.ts` 的
  `ChordLayout.name: ChordText`），因此 overlay 直接复用 `layoutChord` 的整块产物，
  **不重排它的内部**。
- **与 TAB 层的间距**：`SYSTEM_METRICS.chordBandGap`（新常量）。overlay 带的高度
  = 该 system 上实际出现的最高一个 overlay（只有名 vs 名+图两种高度）+ gap；
  **没有和弦的 system 不留这条带**（与 `lyricBandHeight` 的
  「`rows === 0` 时不留余量」同一纪律，`layoutJianpu.ts:86-92`）。
- **横向碰撞**：两个 overlay 的盒子重叠时，**不移动位置**（位置是时间事实），
  而是缩小图形或只画名 —— 具体策略是 **§F 的 F-4 裁决**，推荐「重叠时后一个只画名」
  并发 info 诊断。
- **`layoutChord` 保持 document 级不变**：它仍然是 `GuitarChord → ChordLayout`
  的纯函数（`chord/layoutChord.ts:1-11`），**不消费 `ChordSymbolEvent`**。
  composer 负责「按名查表 → 得到下标 → 调 `layoutChord` → 放到 x,y」。这与 T8.1
  的「chord 是 document 级、退出 voice matrix」架构完全一致（§Q7.3）。

### Q5.4 新增诊断码（只追加）

| code | level | anchor |
|---|---|---|
| `muse.render.chord.name-ambiguous` | warning | 该 `ChordSymbolEvent` 的 **event anchor** |
| `muse.render.chord.symbol-conflict` | warning | 非 carrier 的那条 `ChordSymbolEvent` 的 event anchor |
| `muse.render.chord.diagram-collision` | info | 被降级为只画名的那条事件的 event anchor |

三条都用 **event anchor**（纠偏④）：和弦符号是一个实打实的事件，C3 的 event 分支
可解析且 ownership（`voiceId` 一致）天然成立。

## Q6. Screen 与 Page Layout 分开

### Q6.1 共享的与不共享的

```text
共享：SystemGroup、measure identity、MeasureTimeline、demand width、justify 算法
不共享：availableWidth 的来源、换行阈值、是否分页、页眉页脚
```

即 **System Model 是共享的，packing 的输入参数不共享**。`composeSystem` 接受一个
`PackingPolicy`：

```ts
type PackingPolicy =
  | { readonly kind: 'screen'; readonly availableWidth: number }
  | { readonly kind: 'page'; readonly contentWidth: number; readonly barsPerStaff?: number };

// compose 的产物按 target 包一层（§B.3）；SystemLayout 自身不带 target/policy 字段。
interface ComposedSystemLayout {
  readonly target: 'screen' | 'page';
  readonly systems: readonly SystemLayout[];
}
```

### Q6.2 Screen（本期唯一接 UI 的路径）

- `availableWidth` 仍由 `ResizeObserver` 量出的容器 CSS 宽经
  `computeAvailableWidthUnits(cssWidth, cssPixelsPerUnitAtZoom1, zoom)` 换算
  （`voiceRender.ts:138-144`），**zoom 语义一字不改**；
- responsive packing：窗口变窄 → 每行小节数自动变少（Brief §10.18「交互式 Score View
  自动求解」）；
- `barsperstaff` 在屏幕端**只是上限**，且本期恒不可用（DOC-ONLY，未进 Domain）。

### Q6.3 Page（本期只产数据）

- `contentWidth` 来自 `PageSpec`（纸张宽 − 左右边距），**与窗口无关**；
- 优先尊重 `barsPerStaff`（Brief §10.18「打印：显式 `barsperstaff` > 页面/谱宽约束
  > auto」）：若给定且该行按 demand 放得下 → 强制该行装 N 个 measure；放不下 →
  忽略并按 auto 求解 + 发 info 诊断。**本期 `barsPerStaff` 恒为 `undefined`**，
  这条分支只有测试会走（用合成参数）。

### Q6.4 屏幕 resize 不得反向决定分页（硬规则）

`PageModel` 的输入**只有** `PackingPolicy.kind === 'page'` 产出的
`ComposedSystemLayout`。实现上：

- `pageModel(input: ComposedSystemLayout & { readonly target: 'page' })` ——
  **判别字段在包装类型上，不在 `SystemLayout` 里**（给每个 system 挂一个
  `policy` 字段等于把「这次 compose 的目标」冗余复制 N 份，且 screen/page 两份产物
  会因为这个字段而无法逐字段比对）。传 screen 产物编译期即报错；
- `ScoreView` 的 resize 回调只驱动 screen 管线，**没有任何一条边**能到 `pageModel`；
- 守卫用例：`pageModel.ts` 不 import 任何与 `availableWidth` / `zoom` 相关的符号。

### Q6.5 Page 的输出

每页：`index`（页码从 1 显示、0-based 存）、`contentBox`、`headerBox`、`footerBox`、
`systemIndices`。分配算法：按 system 顺序累加 `box.height + systemGap`，超出
`contentBox.height` 就翻页；**单个 system 不拆**（Brief §2.7.1）。首页的
`headerBox` 高于续页（首页要放标题/演唱/原调-选调/作词-作曲，Brief §2.7.1）。
页脚恒为页码带。

### Q6.6 超高 system 的处理

若某个 system 的高度本身就超过 `contentBox.height`（例如 9 层 group + 多行歌词）：

1. **仍然独占一页**，不拆；
2. `page.overflow = true`；
3. 发 `muse.render.system.page-overflow`（新码，warning），anchor 取该 system 第一个
   layer 的 **voice anchor**（没有更小的可解析单位，且 UI 能定位到是哪个声部把行
   撑高了）；
4. **不自动缩放页面内容**——缩放是 M5 打印的事，M2.5 不引入第二套 scale 语义（D6）。

## Q8. TAB / 简谱「节奏刻印」（beam 分组）（追加小节）

> **动因**：用户对比 Muse Pro 成品谱指出，现有 TAB 时值装饰是**逐音一根符干 + 一条
> 短横线**（视觉上一排 `| | | | |` 加一排 `- - - - -`），很难看。Brief §2.7.2 第 2 层
> 也明写目标版式要求「符干向下 + 八分/十六分 **beam 横梁分组**」，HANDOFF §30.1
> 债务表已把「TAB 相邻减时线不做 beam grouping」记为 T6 遗留视觉 debt。
> 本节把它从「视觉 polish」升级为**有明确规则的刻印任务**，并说明它为什么必须
> 落在 M2.5 内部而不是之后。

### Q8.1 与 M2.5 的关系（为什么是 M2.5 的子任务，不是之后的 polish）

beam 分组**改变 minimum width demand**：

- 现在每个音各自的宽度下界包含「一条减时线 + 尾部留白」
  （`tabDurationGlyphs.ts:251-271` 的 `requiredDurationExtent` 里
  `beamLength + beamGap`；简谱同构在 `jianpuSlotWidths.ts:35-45` 的
  `requiredDashExtent`）。
- 连成 beam 之后，**横梁是组级产物**：组内相邻两音之间只需要「够画一段横梁」的
  宽度，组的**整体**最小宽 ≠ 成员最小宽之和；同时组内要求**等距**（见 Q8.3），
  这是一条新的、**跨列**的宽度约束，现有「逐列 max」的模型表达不了。

而 §Q4 的公共 measure width 正是「逐 voice 求 demand → 跨 voice 取 max」。如果
beam 在 system 之后再做，demand 会被算错两次（先按逐音算一遍 packing，再改成组级，
导致换行结果与最终几何不一致）。**结论：beam 分组必须与公共 measure width 一起
计算**，因此作为 M2.5 的子任务。

**排期位置：T3.5**，依赖链是

```text
T3  timeline（voice 内 onset 累计 + 跨声部共享层）
 └─► T3.5  TAB / Jianpu beam grouping + group-level width demand   ← 本节
      └─► T4  公共 demand solver 一次性消费（逐列需求 + 组级需求一起取 max）
           └─► T5  voice layout 接受 external geometry
```

理由：T4 的 demand solver 必须**一次性**看到最终形态的需求，否则会先按逐音算一遍
packing、再改成组级，换行结果与最终几何对不上。**beam demand 必须在进入 composer
之前独立求出**，composer 只消费数字，不认识 beam。

**beam 不依赖跨声部 shared timeline 是否成立**（重要）：beam 是**声部内部的
engraving**，见 §Q8.2 的拍边界规则。因此 T3.5 只需要 T3 里「voice 内小节内 onset
累计」这一半能力，**不需要** group 的共享层成立；单声部文件（corpus#01/#05/#06）
天然可以 beam。

### Q8.2 beam 分组规则（**待用户确认的裁决**，非格式事实）

> spec §26 / §17 **从未规定** beam 分组规则；ABC 2.1 的「空格断组」写法在 JCX 里
> **无证据**（未核实）。下列规则是**产品决定**，需用户确认后才实现。

分组判据（同时满足才连成一组）：

1. **同一拍内**：组不跨拍边界；
2. **连续**：组内事件在事件序上相邻（中间不得夹入 barline / decoration / unknown）；
3. **时值 ≤ 1/8**：`decomposeDuration` 的 `base ≤ 1/8`（即 `beams ≥ 1`）；
4. **中间无休止**：遇到 `rest`（含 `Z` / `@`）立即断组；
5. **不可分解 / 时值未知不入组**：`unrepresentable` 与 `duration === undefined`
   一律单独成音（与现状一致：两者都不画任何时值装饰，
   `tabDurationGlyphs.ts:33-40`）。

横梁条数：**取组内每个音各自的 `beams` 条数**（八分 1 条、十六分 2 条）；
组内条数不一致时，**公共横梁只画到最小条数，多出的条数画成该音自己的短横梁**
（通行记谱做法；细则见 **§F-10** 的裁决）。四分音符（`beams === 0`）**只留符干，不入组**。
**单音组退回单符干 + 旗**（即现状画法，不画孤立横梁）。

**拍单位由 `M:` 决定**（`Score.meter`，`src/domain/score.ts:13-33` 的
`FractionMeter { num, den }` / `RawMeter { raw }`）：

| `M:` | 一拍 | 依据 |
|---|---|---|
| `x/4`（2/4、3/4、4/4 …） | 四分音符 = `1/4` | 通行记谱；语料 corpus#02 为 3/4，其余多为 4/4 |
| `x/8` 且 `x % 3 === 0`（6/8、9/8、12/8） | 附点四分 = `3/8` | 复拍子惯例 |
| `x/8` 其它（5/8、7/8） | **不分组** | 分组方式有多解（2+3 / 3+2），猜即臆造 |
| `x/2` | 二分 = `1/2` | 同理外推 |
| `M:` 为 `raw`（`C` / `C|`）或缺席 | **不分组，维持现状** | `meterRaw` 已有诊断；spec §8.4 明写 `C`/`C|` 不换算；`spacing.ts:9-10`（P1-3）明写 `Meter` 不参与列宽计算 |

> **P1-3 的窄化（这是一条新裁决，不是「没破」）**
>
> 实际链路是 `Meter → beam group → glyph minimum demand → system packing`，
> 即 **`Meter` 会间接影响最终宽度**。因此不能再写「P1-3 没破」——它被**窄化**了。
> 新表述（须由用户确认，并**记入 `HANDOFF.md` 作为一次语义升级**）：
>
> 1. **`Meter` 仍不得直接决定 spacing / 拍宽**：不存在「一拍 = N 单位宽」这类计算，
>    列宽的直接来源仍只有 `duration` 与字形需求（`spacing.ts:9-10` 原意保持）；
> 2. **允许 `Meter` 用于 engraving grouping**（哪些音连成一个 beam 组）；
> 3. **允许 engraving 产生的 glyph minimum demand 反过来约束最小宽度**——这本来就
>    是既有模型的一部分（`widenFor*Glyphs` 系列已经在做「字形需求抬高列宽」），
>    beam 只是把这个需求从**逐列**变成**组级**。
>
> 实现文件头必须原样写明这三条，否则后人会以为 P1-3 被悄悄破掉。
>
**拍边界用「该声部自己的小节内绝对 offset」判定**（与 §Q3.2 同一套 `Rational` 累计，
零浮点）：一个音落在第几拍 = `floor(onset / beatUnit)`。

> **不看跨声部 shared timeline 是否成功**：`SystemMeasureGeometry.timeline` 缺席
> （§Q3.3 的 D3/D4：结构冲突 / 时值总量不等）说明的是**别的声部**与我对不上，
> 与「我自己这一小节的节奏是否可读」无关，据此禁掉 beam 属于误伤。
>
> **只有该 voice 自身的时值不可知才不分组**——判据落在**该 voice 的该 measure**上：
> ① 该 measure 内存在 `duration === undefined`（`L:` 不可知）；
> ② 该 measure 内存在未建模 effective timing 的 tuplet 成员（`tupletTimingNotModeled`）。
> 两者都让「这个音落在第几拍」失去依据。其余情形一律照常分组。
> `unrepresentable`（`1/3` / `5/16`）**不禁掉整个 measure**：它的 `Rational` 已知，
> onset 累计照常，只是**该音自己**不入组（画不出减时线，见判据 5）。

**简谱减时线用同一分组**：简谱的减时线（`beamFirstOffset` / `beamGap` /
`beamLength`，`metrics/jianpu.ts:30-35`）现在是逐音一条短线；改为**整组一条连续
横线**（长度 = 组首音到组末音的跨度 + 末音字形宽），条数规则与 TAB 一致。
这正是 Brief §2.7.2 第 3 层「减时线按 beam 分组」的要求。

### Q8.3 符干 / 横梁样式

- **符干**：从**第 6 弦下方**（现有 `stringY(staffTop, stringCount) + stemOffsetY`，
  `tabDurationGlyphs.ts:128-131`）向下垂到**横梁所在的 y**，而不是现在的固定
  `stemLength`——同组各音符干因此**等长且底端共线**（横梁是直的，不做倾斜：
  TAB 没有音高高度差，倾斜没有依据）。
- **横梁厚度**：新增 `TAB_METRICS.beamThickness` / `JIANPU_METRICS.beamThickness`
  （现在减时线是零厚度的 `TabSegment` 线段）。第 2、3 条横梁按 `beamGap` 向下叠。
- **组内等距**：组内相邻音的 x 间距相等。这与 §Q3 的共享时间位置**可能冲突**
  （同组内若两音时值不同，按时值加权的 x 就不等距）。裁决：**时值相同的组强制
  等距；时值不同的组不强制**（等距是「同时值序列」的视觉惯例，强行等距会让
  附点八分+十六分的组读错节奏）。→ 见 **§F-10**（组内条数与等距）。
- **`beamLength` 的新语义**：现在它是「单音一条短线的长度」；分组后组内横梁长度由
  相邻音的 x 差决定，`beamLength` 退化为**单音组（退回旗）**与**组末悬挂横梁**的
  长度。常量保留，语义在文件头改写清楚。

## Q7. 测试契约如何演进

### Q7.1 C1/C2/C3 不丢

三条契约的口径（`renderMatrix.helpers.ts` 文件头是唯一权威出处）保持不变：

- **C1**：每个 `RenderItem` 在**该声部的 voice layout** 里恰好一个可见 primary
  节点。M2.5 之后 voice layout 仍然逐事件产 `nodes`，`RenderItem → primary node`
  仍是 1:1。**system 级的新产物（chord overlay、连接括号、measure 框）一律不进
  `layout.nodes`**，因此 C1 的计数不受影响（同 `TabStrokeMark` 的处理，见 §Q5.2）。
