# M2.5 T5.S —— VexFlow shared timing spike（结论文档）

> 日期：2026-10-05 · 基线：`2678563`（T5 封板后）· 结论：**`feasible-with-cost`，no adapter merged**
>
> 用户裁决（2026-10-05）：选择 A —— **M2.5 继续只承诺 Staff tier 1**；tier 2 延后为 **post-M2.5
> enhancement**；不修改 T4 / T5 production code、不实现 renderer adapter、不启动 tier 2 修复。T5.S 作为
> 技术 spike 视为成功完成：它证明了 VexFlow 5.0.0 **能精确接受外部 x**，也证明了**当前 Staff demand
> contract 不足以安全提供这些 x**。

## 1. 要回答的问题

VexFlow 5.0.0 能否在 Staff external geometry 模式下，让 stave 内 timed note 的最终 x 对齐到
`SystemMeasureGeometry.timeline.xByOffsetIndex`（目标：`staff timed event absolute x = stave.x +
xByOffsetIndex[k]`），同时保持 T5 的 `StaffStaveSpec.x / width`、记谱合法性、各类修饰 / 关系布局可接受、
默认 Staff 路径不变、不引入 renderer → composer 的生产接线。

## 2. 依据来源与实验方式

- **源码**：VexFlow 官方仓库 `5.0.0` 标签（提交 `8879d09`，「Release VexFlow 5.0.0」，与项目
  `package.json` 锁定的 `vexflow 5.0.0` 一致），浅克隆在会话 scratchpad，只读。下文 `文件:行` 均指该标签的
  `src/`。本地 `node_modules` 受权限 deny 规则约束，未读取。
- **实验**：VexFlow 5 的全部字形宽度（符头、升降号、附点、谱号）都经 canvas `measureText` 按 Bravura 字体
  实时测量（`element.ts:608-635`），Node 下无 canvas / 字体，宽度全为 0，因此实验在 Chromium（应用运行时
  同为 Chromium）中进行：静态页从 jsDelivr 固定加载 `vexflow@5.0.0` 的 bravura 入口，经只绑定 127.0.0.1、
  只服务 scratchpad 的临时静态服务器提供（实验后已停止）。冒烟页确认 `VexFlow.BUILD.VERSION === '5.0.0'`、
  符头宽 11.8（真实字体）。
- **真实语料**：只以 `corpus#NN` 与聚合数字引用。

## 3. VexFlow 5 实际布局链（源码核实）

| 环节 | 结论 | 依据 |
|---|---|---|
| 音符绝对 x | `tickContext.x + stave.getNoteStartX() + Stave.padding(12)`（居中对齐另加居中偏移） | `note.ts:639-650`、`metrics.ts:167-174`（`Stave.padding: 12`） |
| `TickContext.x` | 普通字段，`setX` 公开；`postFormat()` 只置标记，不写 x | `tickcontext.ts:108-117`、`:280-284` |
| Formatter 写 x 的位置 | 只在 `preFormat`：Pass 1 按 `width + totalLeftPx` 依次累加出**最小间距**，随后 justify / tune 移动 | `formatter.ts:651-708`（Pass 1 `:677-696`） |
| draw 是否重算 x | **不重算**：`StaveNote.draw()` 按 `getAbsoluteX + xShift` 摆符头 / 符干；`Voice.draw()` 只逐个 `drawWithStyle` | `stavenote.ts:1185-1217`、`voice.ts:~299` |
| Beam | 斜率在 `postFormat` 时按当时的符干 x 计算，`draw()` 中若未 postFormat 则延迟计算 | `beam.ts:961-998` |
| Tie | 端点取 `getTieRightX()` / `getTieLeftX()`，二者都基于最终 `getAbsoluteX` | `stavetie.ts:208-222`、`stavenote.ts:725-736` |
| `noteStartX` | `stave.format()` 按开头修饰（小节线 / 谱号 / 调号 / 拍号）实际宽度累加；无修饰时 `x + 5` | `stave.ts:585-621`、`:92` |

## 4. 三条候选路线

### Route A：Formatter 正常排 → 覆写每个 `TickContext.x` → 逐 tickable draw —— **成立**

换算：`tc.setX(stave.getX() + target − stave.getNoteStartX() − Stave.padding)`（target 为 measure 内相对 x，
已含 `contentOffsetX`，**不得**再叠加行首预留）。实测（stave.x = 300、y ≠ 0）：

| 用例 | 目标绝对 x | draw 后 `getAbsoluteX` / 符头 x |
|---|---|---|
| 均匀 `[80,140,230,310]`（含升降号、附点、八分） | `[380,440,530,610]` | 逐位相等 |
| 非均匀 `[80,115,260,310]` | `[380,415,560,610]` | 逐位相等 |
| 和弦 / 二度错位符头 / 休止 / 附点 + 降号 | `[360,450,530,620]` | 逐位相等 |
| `TextNote` 占位（Staff 的 decoration / grace / unknown） | `[340,420,500]` | 逐位相等 |

覆写后再调 `formatter.postFormat()` 不改回；draw 后 x 保持。

### Route B：手动建 `ModifierContext` / `TickContext`，不经 Formatter —— **成立，但无额外收益**

x 同样逐位命中；升降号 / 附点的 `xShift` 与宽度与 Route A **完全相同**（同一组用例逐字段比较为真）。但要
手工复刻 Formatter 的 context 构造（y 值、多声部对齐），维护成本高于 A。

### Route C：Formatter 最小间距作约束、再映射 shared timeline —— **对「x 是否可控」不必要**

A / B 已能精确控制 x；真正的约束是间距**需求**不足（第 6 节），应在 demand 侧解决，不应在 adapter 做二次求解。

## 5. 修饰与关系

- 升降号（实测宽 9.96 / 9.04 / 6.72 / 10，`xShift = −1`）、附点（宽 4）随音符平移，相对偏移不变。
- Tie：实测 tie 跨度 `[351.8, 550]` 恰为 `firstNote.getTieRightX()` 与 `lastNote.getTieLeftX()`。
- Beam：8 个八分音符非均匀目标下，符干 x = 目标 + 11.05，4 段横梁跨度与首末符干一致。**顺序要求**：覆写必须
  早于 `Beam.postFormat` / draw（斜率在那时按符干 x 计算）。注：当前 Staff 主路径**不画 Beam**（beam 分组暂缓）。
- Tuplet：不适用——tuplet 小节在 T3 判 degraded（tier 3），没有 timeline；适配层括号本就按 `getAbsoluteX` 自绘。
- 外部 x **过窄**：VexFlow **不抛错、不自动挪动**，完全服从目标 x → **静默重叠**（实测 4 个带升降号的音符间隔 4，
  重叠 3 处）。adapter 不能依赖 VexFlow 兜底。

## 6. header 坐标与 minimum-spacing probe（关键约束）

### 6.1 stave 内部固定缩进

- **非行首 stave**：`noteStartX = stave.x + 5`，加 `Stave.padding` 12 → 首个音符最早在 `stave.x + 17`，有左侧修饰
  （升降号）时再右移。
- **行首 stave**：T4 行首预留 = 谱号 28 + 调号 7 × 8 + 拍号 20 = **104**。VexFlow 实测（treble + 4/4，`header + 12`）：

| 调号 | C | G | F | D | B♭ | A | E♭ | E | A♭ | B | D♭ | F♯ | G♭ | C♯ | C♭ |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| header + 12 | 77.6 | 97.6 | 96.7 | **108.6** | **106.7** | **119.5** | **116.8** | **130.5** | **126.8** | **141.4** | **136.8** | **152.4** | **146.9** | **163.4** | **156.9** |

  粗体 = 超出 104。VexFlow 每个升降号实测约 11，T4 按 8 估算，**≥ 2 个升降号的调号**行首预留即不足（tier 1 下同样
  存在：行首小节内容被挤窄，非 T5 引入）。另测：无修饰 `noteStartX − x = 5`，仅谱号 31.8，谱号 + 拍号 65.6。

### 6.2 真实语料 probe（T5 external 目标 vs VexFlow Pass 1 最小间距）

对所有 Staff shared 小节，以 T5 external `StaffLayout.slots` 的最终 x 为目标，与 VexFlow `Formatter.format(…, 0)`
（只跑 Pass 1，即最小间距）比较：

| 范围 | 小节 | 相邻锚点间距 | 小节尾（末音右缘 vs `endX`） | 小节头（首音 vs VexFlow 最小起点） |
|---|---|---|---|---|
| corpus#05 @ 960 | 16 | 47 对：exact 0 / wider 47 / **narrower 0** | 16 / 16 放得下 | **11 过窄，最大缺口 24.21**；5 个行首小节全部放得下 |
| corpus#05 @ 16（每小节一行，均为行首） | 16 | 47 对全部 wider | 16 / 16 | 16 / 16 放得下 |
| fixture @ 960 | 14 | 42 对全部 wider | 14 / 14 | **6 过窄，最大缺口 17** |
| fixture @ 16 | 14 | 42 对全部 wider | 14 / 14 | 14 / 14 |

结论：**小节内部间距从不不足**（`staffMeasureSpacing` 的最小列宽 40 本就按 VexFlow 标定）；冲突**只在非行首小节的
第一个 onset**——T4 让首个 onset 紧贴「measure 左边界 + lead'」，VexFlow 却要求 ≥ 17 + 首音左侧修饰的内部缩进，
缺口即为二者之差（17 = 无修饰；24.21 = 带升降号）。按 Route A 直接写入这些 x，11 / 16 的非行首小节首音会压到前一
小节的收尾小节线上。

## 7. 结论：`feasible-with-cost`

- **feasible 的部分**：TickContext.x 稳定可控；Formatter 后覆写保持；draw 后绝对 x 保持；升降号 / 附点 / 休止 /
  和弦 / tie / beam / TextNote 无结构性错误；不需要改 VexFlow 源码；adapter 可限制在
  `renderer/integrations/vexflow/**`；默认 Staff 路径可保持不变。
- **cost 的部分（tier 2 的三个 prerequisite）**：
  1. **Staff demand calibration（T4 范围）**：Staff 小节的 lead 需求须计入 VexFlow 内部缩进（≥ 17 + 首音左侧修饰），
     行首预留须按实际升降号宽度（约 11 / 个）或由 renderer 注入的测量接口计算；notation 层不得 import vexflow，
     这是架构层面的改动。
  2. **Staff 契约扩展**：`StaffLayout` 目前不标记哪些小节是 shared，`StaffEventNode.slot` 也不含 x（只能按
     `slotIndex` 回查 `layout.slots`）；需给 `StaffStaveSpec` 加可选的「共享时间轴」标记，或由 T8 / T9b 把公共几何
     直接交给 renderer。
  3. **renderer adapter**（预估 40–60 行，限于 `renderer/integrations/vexflow/**`）：只对 shared 小节在
     `formatToStave` 之后、draw 之前按第 4 节换算覆写 x（padding 取 `Metrics` 的 `Stave.padding`，不写死 12）；
     tier 3 小节仍交给 Formatter；将来加 beam 时覆写须早于 beam postFormat。

## 8. 为什么 M2.5 仍成立（Staff tier 1）

tier 1 只承诺 `StaffStaveSpec.x / width` = 公共 measure 几何，已由 T5 测试与 mutation 钉住；stave 内部仍由 VexFlow
Formatter 自排（带它自己的 17 单位缩进与 header），不会重叠，只是 Staff 音符不与 Jianpu / TAB 逐音对齐——这正是冻结
方案 §Q3.5 与 E-1 预设的「未证明前只承诺 tier 1」。**T6 / T8 期间不得顺手实现 tier 2**；它作为 post-M2.5 enhancement
单独立项，以第 7 节三个 prerequisite 为前置。

spike 期间未修改任何仓库文件（生产代码、`system/**`、三个 voice layout、Domain / parser / serializer、renderer 均为
零改动）；实验脚本与 VexFlow 克隆只在会话 scratchpad，不入库。
